1. 项目背景

城市街道平均占据城市建成区面积的 30% 左右，但这些公共空间长期被锁定在"以机动车为中心"的单一用途上。随着城市可持续发展、行人友好、公共健康、社区凝聚力等议题在世界范围内成为城市更新的核心议程，越来越多的城市开始尝试将街道空间在特定时段、特定情境下临时让渡给行人、休闲、商业摊位、文化活动等非机动车使用。

典型实践包括美国多个城市的 Open Streets / Slow Streets 计划、费城的 Playstreets 暑期儿童游戏街、纽约 SoHo 周末步行街、巴黎的 Rue aux écoles（校门步行街）等。这些项目共同指向一个核心理念：街道应当是动态的、可被重新分配的公共资产，而不是一成不变的基础设施。

然而，目前城市规划部门在做这类决策时，普遍依赖以下几种方式：

  • 经验判断：靠规划师或社区组织者的直觉选街道，缺乏量化依据；
  • 申请驱动：等社区主动提交申请，无法主动识别潜力街段；
  • 事后评估：项目落地后才用人工调查或交通量数据评估效果，难以提前预测影响。

这种模式带来三个问题：

  1. 潜力街道被忽略——很多本应成为优秀候选的街道因为没人关注而错过机会；
  2. 资源分配低效——有限的封街许可、人员、设施往往分配给申请最积极的社区，而非最适合的地点；
  3. 风险评估缺失——不少临时关闭后才发现影响了急救通道、瘫痪了当地交通，造成不必要的争议。
核心痛点：城市需要一套事前的、数据驱动的、可解释的工具，帮助决策者在数千条候选街道中识别"何时、何地、为何"可以临时灵活使用。这正是本项目要解决的问题。

2. 项目目的与目标

本项目立项之初的核心目标，是构建一个面向城市规划者、社区组织和公民利益方的数字平台，将街道从静态基础设施重新定义为"承载市民生活的活态框架"，使街道空间能够响应时间、情境与社区需求动态调整。

2.1 总体目标

建立一个名为 Flexible Street Platform 的数据驱动评分与决策辅助系统，使城市能够：

  • 识别每条街道在不同时段的灵活使用潜力（Flexibility Potential）；
  • 推荐Flex Window——具体的、可落地的临时空间重分配时段；
  • 整合多源数据（POI 密度、交通模式、天气、活动、节日、视觉感知）形成单一可解释的指标；
  • 向规划者、社区组织、公众分别提供差异化的可视化与解释。

2.2 核心概念：Street Anchor（街道锚点）

项目的理论基础是"街道锚点"：那些可预测地产生人流和社交活动的设施——学校、社区中心、图书馆、热门餐饮、交通枢纽、文化机构等。锚点决定了街道在不同时段的"节奏"——学校放学时校门口街道应该让渡给步行接送；周末市集启动时商业街应转为步行优先；夜间文化活动开始时餐饮街应延伸至室外。

平台的根本任务，就是识别这些锚点的影响范围与时间窗口，并据此推荐 Flex Window。

3. 方法与技术实现

3.1 系统架构

平台采用前后端分离 + 边缘预计算的轻量架构：

层次技术选型职责
前端 UIReact 18 + TypeScript 5.6 + Vite 5.4 + Tailwind CSS地图渲染、面板交互、可视化
地图引擎Mapbox GL JS 3.7 + 自定义矢量瓦片街道、POI、活动叠加层
评分计算客户端 TypeScript 实时计算FSI 评分、安全约束、簇群检测
数据库Supabase (PostgreSQL + PostGIS) + RPC 边界查询POI、AI 分数、活动、Playstreets
AI 模块LLaVA 7B（离线预跑，结果存表）街景图像感知评分 + 关键词
外部 APIOpen-Meteo（天气）、Ticketmaster（活动）、Google Street View Static实时上下文数据
部署GitHub Actions + Vercel-style 静态托管CI/CD、零运维

所有评分逻辑都在浏览器端实时计算，不依赖服务器算力。这一选择让系统能够：

  • 支持任意 POI 加载量与街道密度，无 backend rate limit；
  • 用户切换时段、天气情境时分数即时刷新（<100ms）；
  • 所有规则可审计、可解释——每条街的最终分数都能完整反推。

3.2 FSI 评分模型（Flexibility Score Index）

FSI 是平台的核心算法，用以量化每条街道在当前情境下的"灵活使用潜力"。它以沿街 POI 密度为基础，按"垂直走廊衰减模型"计算各类别原始得分，经 sigmoid 归一化后输出 0-100 的分数。

3.2.1 两个评分维度

综合分仅由以下两个维度构成：

维度覆盖类别走廊宽度含义
Commercial餐饮 + 文化 + 金融35 m商业活力——餐厅、咖啡馆、银行、剧院、画廊等沿街商业 POI 越密集，越适合商业型 Flex（夜间餐饮街、周末市集等）
Community教育 + 社区 + 宗教 + 公共安全 + 医疗150 m社区机构密度——学校、社区中心、教堂、图书馆等。走廊更宽，因为机构两个街区外仍能产生人流

3.2.2 信息辅助标签：Mobility（不参与评分）

除上述两个评分维度外，平台还会单独计算并展示一个 Mobility 标签——基于 SEPTA 公交 / 地铁 / 通勤铁路站点在 80 m 走廊内的密度。它有意被排除在综合分之外，原因是：好的交通可达性是举办 Flex 活动的先决条件（让参与者能到场），但这一点本身并不构成"应当关闭这条街"的理由。把它单独以标签形式呈现，让规划者在选定高分街段后可以进一步判断"这条候选街是否便于公众抵达"，但不会让"附近有地铁站"这一事实人为推高一条无活动潜力街道的分数。

3.2.3 计算公式

raw = Σ exp( −dperp / DECAY )     (落入走廊内的所有 POI)
score = 100 × ( 1 − exp( −raw / saturation ) )     (sigmoid 归一化到 0-100)
composite = max(commercial, community)     (mobility 不参与)

关键设计：

  • 距离衰减：远离街道的 POI 权重指数下降，避免对侧街区的 POI 误判贡献；
  • Sigmoid 饱和：避免"POI 越多分越高"的线性失真——5 家餐厅 vs 50 家餐厅在街道使用价值上接近，但线性求和会让后者拿到 10 倍分数；
  • 取最大而非求和：商业型与社区型本质是不同活动模式，一条街只需要在一种维度上突出即可，不应靠"两边都中等"叠出高分。

3.2.4 局部突出度奖励（Prominence Bonus）

除了绝对密度，平台还引入邻域比较奖励：在 ~440m 邻域内，若某条街的原始 POI 求和显著高于邻居中位数，给予最多 +10 分的"局部领头"奖励。这避免了 POI 稀疏区域的"小高峰街道"被淹没——例如西费城的某条主商业街，POI 总数虽不及市中心，但已是周边唯一的活动汇聚点，理应被推荐。

3.2.5 校准方法

所有饱和参数都通过反向拟合费城 Playstreets 数据集得到。Playstreets 是费城官方暑期儿童游戏街计划的真实历史数据，作为"已被验证可灵活使用"的正例。校准目标：让 50%-75% 的 Playstreets 街道在工作时段下能拿到 ≥75 分。校准工具内置在 src/lib/fsiCalibrate.ts，可在控制台输出当前参数对应的 P50 / P75 分布。

3.3 实时调节因子

FSI 基础分代表"理论潜力"，但实际是否适合现在关闭，还取决于当下情境。平台引入 4 类乘性修正：

因子取值范围逻辑
Traffic（交通）0.50 – 1.0按道路类型（highway/arterial/collector/local）× 时段（早/午/晚/夜）查表。高速路在早高峰 ×0.50，背街小巷在夜间 ×1.0
Weather（天气）0.20 – 1.0Open-Meteo WMO 天气码映射。晴朗 ×1.0，小雨 ×0.7，雷雨 / 大雪 ×0.2
Events（附近活动）1.0 – 1.20Ticketmaster 拉取季节性活动（游行、节日、马拉松），300m 内 ×1.20，1km 内 ×1.10，2.5km 内 ×1.04
Holiday（节日）1.0 – 1.25费城本地节日日历——Mummers Parade、感恩节、Penn Relays 等当日全城加成
final = composite × traffic × weather × events × holiday

这种独立可解释的乘性结构，使得详情面板能完整列出"为什么这条街今天得分变高/变低"——交通拥堵 ×0.65 给一个橙色提示，附近马拉松 ×1.18 给一个绿色加成。

3.4 AI 街景视觉感知

除 POI 密度外，平台还集成视觉感知维度。我们使用 LLaVA 7B 多模态视觉语言模型，对每条已分析街道的 Google Street View 图像进行：

  1. 0-100 sensory score——综合判断该街道的"宜步性"；
  2. 3-5 个关键词标签——例如 "vibrant"、"residential quiet"、"transit-heavy"，作为详情面板的语义标签。

AI 分数与 POI 分数的融合策略：

ML × 0.6 + AI × 0.4  (若该街道有 AI 分析结果)
ML 单独  (无 AI 时回退)

AI 分数离线预跑后存入 Supabase 的 street_ai_scores 表，运行时按需分页加载（1000 条/批），避免实时模型调用的高成本与延迟。

3.5 所有权与可关闭性

同样的 POI 密度，城市能否真的关闭这条街还取决于产权归属。平台基于费城街道中心线数据集的 responsibl 属性识别 14 类 agency，归并为三档：

档位包含 agency说明
City-managed · 可直接关闭CITY, FAIRMOUNT PARK, PHA, PIDC, FAM市政府权限，无需跨机构审批
需机构审批SEPTA, DRPA, BCBC, TOWNSHIP跨机构协调，时间成本但非否决
不可关闭STATE, PRIVATE, AIRPORT, STRICKEN 等评分照常计算，但 UI 标灰提示

注意：所有权不进入分数，只作为"可执行性"独立标签呈现。两条潜力相同的街道得分相同，但 UI 会清楚指明哪条可以立刻封闭，哪条需要走 SEPTA 审批。

3.6 安全约束层（紧急通道一票否决）

在试点过程中我们意识到，一个潜力分数再高的街道，如果是医院或消防站门口的必经之路，就绝不能被推荐关闭。为此引入一个独立的安全约束层：

设施类型OSM amenity tag缓冲距离语义
医院hospital150 m救护车进出 + 急诊通道
消防站fire_station90 m消防车出动通道
警察局police70 m警车出动通道

实现逻辑：对每条街道，遍历 POI 中的紧急设施，计算"街道中线到设施"的垂直最短距离；若任一设施距离小于该类阈值，整条街标记为 vetoed=true。

UI 表现：

  • 地图：被否决街道渲染为纯品红色（#EC4899），刻意选在 FSI 分数色谱（红→橙→黄→绿）之外，不会与"低分红"混淆；
  • 详情面板：粉红色 Siren 图标横幅，标注"Cannot close · emergency access route"+ 设施类型 + 实际距离；
  • 图例：在 "Closure Constraints" 区块独立列出。
设计哲学：该约束不参与分数计算（理论潜力照常评出），而是作为"覆盖层"独立呈现。这样既保留了原始数据，也清晰传达了"高潜力 ≠ 可关闭"这一核心区分。

3.7 簇群协调检测（Closure Cluster Detection）

项目后期我们识别出一个更微妙的风险：单条街道关闭通常不会瘫痪城市路网（网格冗余足够），但多条相邻的高分街道同时关闭，可能造成局部网络断裂。例如同时关掉 Walnut、Chestnut、Sansom、Spruce 4 条平行街，整个 Penn 校园南北向通道将塌陷。

为此实现 findClusters() 函数——基于共享路口的并查集（Union-Find）算法：

  1. 筛选候选：score ≥ 75 + closeable + 未被紧急通道否决；
  2. 建立空间哈希：所有街道端点按 35m 网格分桶；
  3. 合并：对相邻桶内端点距离 ≤ 35m 的两条街执行 union；
  4. 分组：连通分量 ≥ 3 条街，标记为"closure cluster"。

UI 表现：簇成员街道在 FSI 颜色下方叠加青色光晕（#06B6D4，opacity 0.32, blur 2），既不抢夺分数颜色又能一眼识别簇范围。详情面板显示 "Coordinate group · N streets" 徽章并解释含义。算法复杂度近似线性，对视口内任意街道密度都流畅。

4. 项目成果与结论

4.1 完成度评估

项目在核心功能层面已完整交付立项目标，并在试点过程中迭代出若干立项时未明确预期的关键能力。具体成果包括：

  1. 建立了一套可解释的多维 FSI 评分体系。综合分由 commercial 与 community 两个评分维度构成（取最大值），mobility 作为附加信息标签独立呈现。所有维度均经 sigmoid 饱和归一化与邻域突出度奖励，输出 0-100 分数。计算全部在客户端实时完成，毫秒级响应。
  2. 融合了实时上下文调节。交通、天气、活动、节日 4 类因子以乘性方式叠加在基础分之上，使同一条街在不同时段、不同天气、不同社会事件下产生不同推荐——这恰恰是立项时强调的"adaptable to time, context, and community needs"的核心实现。
  3. 引入了 AI 视觉感知补强。LLaVA 7B 模型对 Google Street View 图像的离线分析，让评分不仅看"街上有什么 POI"，还能看"街道实际看起来怎么样"——是密集商业、是安静住宅、是过境通道。两种数据源以 6:4 加权融合。
  4. 明确区分了"潜力"与"可执行性"。所有权 / 可关闭性独立呈现，不污染分数；紧急通道一票否决独立呈现，不污染分数；簇群协调提示独立呈现，不污染分数。这使得平台输出的每个数字都有清晰单一的语义。
  5. 建立了基于真实数据的校准闭环。所有饱和参数通过反向拟合费城 Playstreets 历史数据得到，让模型"对得上"已被城市实践验证过的优秀候选。
  6. 提供了三层可视化与交互：地图全局色块 + 簇群光晕 + 紧急否决标识 → 街道详情面板（分数、子分数、AI 标签、影响因子、可关闭性）→ 因子点击展开解释。从城市级俯视到单街道决策都有对应视图。

4.2 关键设计决策的反思

取最大而非求和的综合分

这是反直觉的——直觉上"商业 + 社区"双高的街道应该最有价值。但实践校准发现，街道使用模式具有排他性：商业型 Flex 与社区型 Flex 是两套截然不同的活动剧本（夜间餐饮街 vs 校门接送步行街），强行叠加会让"两边中等"街道淹没真正"一边突出"的街道。最终采用 max(commercial, community)。

所有权不进入分数

立项早期讨论过"私有街道直接给 0 分"，但执行下来发现这破坏了模型的可比较性——同一条物理潜力的街道在不同所有权下应得到相同的活动价值评分，所有权变化只影响"能不能落地"，不影响"该不该考虑"。最终采用"分数照算 + 标识独立显示"。

簇群作为协调提示而非否决

簇群检测最初考虑设为"扣分"，但反复推演发现：簇群本身不是坏事——它意味着这一带都适合 Flex，而非簇内任何单条街应该被排除。真正需要的是提示决策者"这是个集团动作"——单关一条 OK，要关多条得统一规划。最终采用青色光晕 + 解释横幅，信息透明而不阻断决策。

4.3 局限与诚实陈述

项目刻意未解决的问题，记录在此供后续工作参考：
  • 路网拓扑感知缺失：单条街关闭后车辆能否绕行、需绕多远，平台无法判断。详见 §5.2。
  • 单行道未识别：当前矢量瓦片不含 oneway 属性，单行道关闭的影响被低估。详见 §5.3。
  • 无用户反馈通道：当地工作人员无法直接在平台上指出"这里平台错了"。详见 §5.1。
  • 无纵向数据：每次刷新都是当下快照，无法追溯一条街道在过去 3 个月的评分趋势。
  • 仅限单城市：硬编码费城坐标和数据源，多城市推广需要数据接入层抽象。

5. 未来工作展望

基于当前已交付的功能集与试点反馈，下面五个方向被识别为最具价值的后续研发投入。按"价值 × 可行性"综合排序。

5.1 用户反馈机制（Citizen / Operator Feedback Loop）

当前平台是"单向输出"——算法推荐什么，使用者只能接受或忽视。但实际场景中，当地机构工作人员往往掌握平台无法捕捉的实地信息：某家算法标记为"hospital"的设施实际上已迁址三年；某条算法识别为高分的街道两侧正在施工根本无法关闭；某次推荐忽略了周边居民近期的强烈反对。

设计设想

  1. 反馈入口：在每条街道的详情面板增加 "Feedback / Report Issue" 按钮；
  2. 反馈类型分类：
    • 分数偏差（"实际不像 80 分这么好"/"被低估"）
    • POI 错误（"这家店已关门"/"漏标了一所学校"）
    • 紧急通道误判（"这里其实是急救必经之路"/"这家不是真正的医院"）
    • 活动 / 节日漏标
    • 所有权错误
    • 其他自由文本
  3. 持久化：Supabase 新增 street_feedback 表（街道 ID、反馈类型、文本、提交者邮箱、时间戳、状态）；
  4. 审核与回路：管理员后台每周 review 一次，确认有效后：
    • 分数偏差 → 加入 calibration 数据集，下次重新拟合饱和参数；
    • POI 错误 → 推送给 OSM 编辑社区或直接修正 Supabase POI 表；
    • 紧急通道误判 → 调整 amenity 标记或局部 buffer。
  5. 透明度：在街道详情面板下方展示"过去收到 N 条反馈"，已处理 / 待处理状态可见，建立公众信任。

价值

这一机制将平台从"专家工具"转变为众包验证的协作系统，长期能形成"算法预测 → 实地验证 → 模型迭代"的健康反馈闭环，是数据驱动城市治理的关键环节。

5.2 路网可达性与绕行成本分析（最关键的未来工作）

典型场景：假设算法推荐关闭 34th Street（Penn 校园主干道）作为周末步行活动场地。这条街本身得分很高，紧急通道判断也通过——但它恰好是周边居民通往 Penn Presbyterian Medical Center（宾大医院）的最短驾车路径。一旦关闭，急诊车辆需绕行 6 个街区、增加 8-12 分钟车程。在心梗、中风等黄金时间敏感的医疗场景下，这种延误可能直接危及生命。

当前平台无法察觉这种风险，因为紧急通道判断仅基于"街道距设施的直线距离"，而非"街道是否在通往设施的最短路径上"。这是纯几何检查 vs 网络拓扑分析的本质差异。

技术路径（按工程复杂度排序）

方案 A：静态预计算（推荐先做）

  1. 从 OpenStreetMap 抓取费城完整路网（含单行道方向）；
  2. 用 Python 的 OSMnx + NetworkX 构建有向图；
  3. 对每条边离线计算 edge betweenness centrality——衡量"该街道有多少最短路径要经过"；
  4. 额外计算"关键医院 / 消防站可达性指标"——以每个紧急设施为终点，计算各街道是否在 N% 的最短路径中；
  5. 将结果作为 criticality_score 列存入 Supabase 街道表；
  6. 客户端读取该列，criticality 高者：① 进入综合分作为 networkMod 折扣；② 详情面板显示"此街道是 X 个紧急设施的关键路径"。

优点：一次性预计算，运行时零开销，结果稳定可解释。缺点：路网或紧急设施变动需重新预跑。

方案 B：动态查询（推荐配合 A 做精细化）

  1. 用户点击某条街表示"想模拟关闭"；
  2. 调用 Mapbox Directions API 或 OSRM，请求"以该街道为禁行边"的最短路径；
  3. 对比"原始最短路径"与"绕行最短路径"的距离 / 时长比；
  4. 若比值 > 1.5（绕行超过原路 50%）→ 详情面板红色警示"Closing this would extend ambulance routes by N%";
  5. 对所有附近紧急设施做该计算，列出"对哪些设施影响最大"。

优点：精确、所见即所得。缺点：API 成本（Mapbox 按调用收费）+ 延迟。

方案 C：多街道联合关闭模拟

结合 §3.7 的簇群检测，进一步分析"如果整个簇被关闭"对路网的累积影响。这是 Flex Window 真正落地为成片活动时（例如开幕式式的多街道集中封闭）的关键决策辅助。

价值

解决这个问题，平台才能从"推荐什么街道适合 Flex"升级为"在保障公共安全前提下推荐什么时间什么街道适合 Flex"——后者才是城市规划部门真正可以信赖的决策依据。

5.3 单行道识别

当前 Mapbox 矢量瓦片仅含 stname、responsibl、objectid，没有方向性属性。但单行街关闭的影响远大于双向街：

  • 双向街关闭 → 车辆原地反向绕行，影响小；
  • 单行街关闭 → 车辆无法掉头，必须绕到下一条同向街，可能多走 2-4 个街区。

实现路径

编写一次性 Python ETL 脚本，从 OpenStreetMap Overpass API 拉取费城所有 oneway=yes 街道，按几何重叠匹配到现有 Mapbox 街道的 objectid，新增 is_oneway 列灌入 Supabase。客户端按需读取，单行道在详情面板显示"⚠ 单行街——封闭影响周边 2-4 街区车流"。

这个增强可独立于 §5.2 完成，工作量较小但价值明显。

5.4 纵向数据采集与模型迭代

当前平台输出的是当下快照。无法回答以下关键问题：

  • "这条街上周末分数是多少？" — 无历史；
  • "上次推荐关闭这条街，实际效果如何？" — 无追溯；
  • "哪些街道在最近 6 个月持续被推荐但从未被采纳？" — 无趋势分析。

建议

  1. 定时快照：每日凌晨自动遍历全城街道，将当日 FSI 与所有调节因子持久化到 fsi_history 表；
  2. 试点区传感器：在 Center City 与 West Philadelphia 的部分街道部署低成本人流计数器（OpenCount 之类的开源方案）或与现有市政摄像头集成，记录 Flex Window 前后实际人流 / 车流变化；
  3. 评估对照：将传感器实测数据与 FSI 预测值做相关性分析，识别"算法持续高估 / 低估"的街道类型，据此迭代模型权重；
  4. 趋势可视化：详情面板增加 90 天分数曲线图，让规划者识别"这条街是稳定高分还是季节性突涨"。

5.5 多城市推广

当前实现深度依赖费城特定数据源（responsibl agency 命名、Playstreets 数据集、本地节日日历）。要推广到其他城市，需做：

  1. 数据接入层抽象：将"街道几何 / POI / 验证集 / 节日"封装为可替换的 provider 接口；
  2. 城市配置档：每个新城市建立配置文件，指定 Mapbox 瓦片 URL、Supabase 表、节日列表、agency 命名映射；
  3. 本地化校准：每个城市需用其本地"已验证 Flex 街道"做一次 saturation 重新拟合；
  4. 多语言 UI：当前 UI 字符串硬编码为英文，需要 i18n 抽取。

建议先与一两个具体城市（例如纽约或波士顿）合作，在第一次推广中固化抽象层，然后才能规模化接入更多城市。

5.6 多模式平衡与无障碍

当前平台关注的是"机动车 vs 行人"的二元转换。实际街道使用涉及更复杂的多方利益：

  • 骑行：自行车、电动滑板车的通行需求；
  • 无障碍：轮椅、视障人士的通行权与安全；
  • 配送：电商配送车、垃圾收运车、紧急维修车的接入需求；
  • 商家：沿街商业的客流送达 vs 停车需求；
  • 居民：当地居民的车辆出入与生活影响。

未来可考虑在 FSI 之外，建立多目标决策矩阵——不再追求"一个综合分"，而是多维雷达图（车流影响、行人收益、商业影响、居民便利、无障碍、配送可达性），让规划者按当下优先级权衡。这与"灵活道路"的本质——多元利益的动态协调——更加吻合。
